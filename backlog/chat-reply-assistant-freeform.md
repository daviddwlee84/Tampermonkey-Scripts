# Chat Reply Assistant 自我續話與自由續聊

**Status**: deferred
**Effort**: L
**Related**: [TODO.md](../TODO.md) · [目前使用方式](../userscripts/chat-reply-assistant/README.md)

## Context

2026-09-25，使用者希望未來可讓模型較自由地聊天，包含自己說完後主動接續。這與目前「回覆新的對方訊息」不同，先保留為 future work。

v0.3 的自動回覆以新的對方 turn 為觸發單位；每次 run 需手動開始，可設定倒數與送出次數。Gemini 空白 `/app` 的破冰開場是特定例外，並不表示一般對話能在沒有對方回覆時持續自說自話。

## Investigation

- 新模式需要獨立的續話理由：補充上一則、等待太久後追問，或依目標推進話題，不能把每次 DOM mutation 都當觸發。
- 自己的訊息與 AI 生成的建議必須保留來源，避免把模型剛產生的句子再次當成新的對方訊息。
- 目前模型與網站雙層往返已可能增加訂閱／token 用量；更自由的模式需要看得到的停止理由、輪數與剩餘預算。
- 使用者輸入、網站尚在生成、分頁離開前景、路由／帳號變更、送出結果不明，都應中止候選與倒數。

## Options considered

| 方案                   | 用途                       | 代價                                               |
| ---------------------- | -------------------------- | -------------------------------------------------- |
| 手動「接續我上一則」   | 最小且可驗證的自我續話入口 | 需要每次按鈕觸發                                   |
| 指定目標的有限回合模式 | 例如角色演練或共同構思     | 需要進度／達標／偏題判定，不能只靠 LLM 自述        |
| 閒置時間後自由續聊     | 自動維持對話               | 容易打擾、重複或在串流停頓時插話，時機判斷較不可靠 |

## Open questions

- 什麼情境應接續自己，而不是等對方？是否只適用 AI 聊天網站？
- 如何判斷話題完成、重複、偏題或對方不願繼續？
- 使用者選擇無限輪數時，還需要哪些可觀察的 token／時間停止條件？
- 是否沿用三候選加 Jev，或使用專門的續話品質判定？

## Decision

2026-09-25 deferred。先維持 v0.3 新對方 turn 與 Gemini 開場的清楚邊界，不把舊的自動生成偏好轉成更廣的送出權限。

接續第一步：建立少量不涉及真實他人的離線對話案例，比較「手動接續上一則」與「固定目標、最多數輪」兩種流程；定義重複與停止的可檢查條件後，再決定是否需要計時觸發。
